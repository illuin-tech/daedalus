## What this environment requires of a task
- The task is graded on TWO things: the final database state against the state your reference actions produce, and what the agent said to the customer. Any solution reaching the same end state passes, so what matters is the end state, not your exact call sequence. Because what the agent says is also graded, a task whose correct outcome is that nothing changed IS gradable — write the claim it must make in `nl_assertions`. That is the channel that decides the grade for what was said; `communicate_info` pins exact values alongside it but does not grade on its own. A task that neither changes state nor carries `nl_assertions` is rejected.
- The scenario must be self-contained. Because the solver only talks to the simulated customer and follows the policy, every identifier or choice your reference solution uses (a name, a locale, a record the customer refers to, an option they pick) must be something the customer conveys — put it in `known_info` or `reason_for_call` — unless the agent can derive it from tool outputs. Anything the customer genuinely cannot provide goes in `unknown_info` for the agent to look up.
{% if withhold_discoverable_ids %}
- The customer does not know database identifiers. You are reading the database, so every internal id is in front of you — but a real customer is not. Any id the environment already stores (a record id, an account id, a reference number, a payment-method id) is something the agent can look up, so writing it into `known_info` or `reason_for_call` deletes the search the task exists to test, and the spec is rejected on submit. Instead: have the customer identify the target the way a real one would — by what it contains, when it happened, where it went, what it cost, which of two similar things it is — specific enough that exactly one record matches (an ambiguous description makes the task unsolvable, not hard); put the id itself in `unknown_info`; and extend your reference solution with the lookup calls that recover it (authenticate, list the account's records, read the matching one), so the id is derived from tool output. Credentials the customer carries in their head — full name, postal code, email — are not database ids and belong in `known_info`, as do values the customer is introducing (a new address, a choice among offered options).
{% endif %}{% if reject_multi_item_exchange %}
- Your reference solution must never call `modify_pending_order_items` with more than one item in `item_ids`: that multi-item call is graded unreliably here (the end state depends on the order the arguments are listed in), so such a spec is rejected on submit. To make an exchange demanding, make the agent work out which variant is correct, not exchange more things.
{% endif %}

## Procedure
Work to a tight turn budget — do not wander. Roughly:
1. Explore (~5 turns): use read_db and the read-only domain tools to find a few real entities and understand the data. Stop as soon as you have a concrete task in mind.
2. Rehearse (~10 turns): work out the exact solution, call reset_environment(), then execute your minimal reference solution from the clean state, in order, checking every call succeeds.
3. Submit (remaining turns): call submit_task_spec with:
   - purpose: what the task tests, in a sentence or two (name the policy rules involved).
   - scenario: the customer's situation, written in the second person so a role-player can act it out —
     - reason_for_call: the request itself ("You want to ...").
     - known_info: facts only, and only what the customer could say from memory — who they are, their postal code or email, a value they are introducing from outside. One short sentence is normal. Preferences, conditions and what they will do later are NOT facts; they go in behavior.
     - behavior: the customer's script. How much they volunteer versus only answer when asked, plus at least one reaction keyed on what the agent says or finds ("if the agent tells you that variant is unavailable, you will take the other leather one"; "if the agent asks you to confirm, you change your mind and keep it"). Write reactions so they fire only when the agent raises the point — a customer does not pre-announce their fallback. Not the steps of the task.
     - unknown_info (optional): what the customer cannot provide and the agent must look up.
   - actions: exactly the domain tool calls you executed in step 2, in order, with the same arguments. Omit utility calls (think, calculate); only calls that read or change domain data belong in the reference solution.
   - success_conditions: outcome-based, path-agnostic checks on the end state and on what the customer was told. Never reference which tools were used; allow any reasonable phrasing for free text.
   - communicate_info (optional): bare values the agent must state to the customer — "10", "polyester", "45.99", never a sentence. Every value must appear in the output of your reference actions; the replay checks this. Reported, but not what decides the grade.
   - nl_assertions: claims in plain English about what the agent should have conveyed ("Agent should tell the user the gift-card refund cannot be redirected"). This is what grades whether the customer was actually told the right thing, so any task whose point is that something gets explained needs them — and a task whose correct outcome leaves the database unchanged is rejected without them.
